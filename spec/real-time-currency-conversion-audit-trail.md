**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:** *(fixed — carry through unchanged, do not reinterpret)*

- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:**
- `src/backend/OuterloopLabApi.sln` — the .NET solution that must exist at exactly this path, generated with `dotnet new sln` + `dotnet sln add` (not hand-authored); the backend project is added to it and every build/test command invokes this `.sln`, never the `.csproj` directly.
- `src/backend/Program.cs` — ASP.NET Core startup; this is where the control-plane ARM provisioning (`Azure.ResourceManager` / `Azure.ResourceManager.CosmosDB`) and the token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` / `CreateContainerIfNotExistsAsync` must run before the web app starts serving.
- `src/backend/` — the C# backend project (the one added to the solution), targeting `net10.0`; will host the conversion endpoints, the external-provider client, and the Cosmos data-plane audit CRUD.
- `src/frontend/` — the React (Vite, Node 24.*) app; its production build emits `index.html` (or equivalent) that must carry the `__VITE_API_URL__` placeholder token for runtime replacement by a generic entrypoint script.
- `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` — the authoritative registry of environment variable keys (`AZURE_MANAGED_IDENTITY_CLIENT_ID`, `CURRENCY_API_BASE_URL`, `VITE_API_URL`, endpoint URLs, resource names) that every configuration binding must use exactly; no local settings files as fallbacks.

**In Scope:**
- Currency conversion API in `src/backend`: accepts amount, source currency, target currency; returns the converted amount together with the exact rate, provider identity, provider date/sequence marker, and server execution timestamp used.
- External rate provider client that reads `CURRENCY_API_BASE_URL` (defaulting to `https://frankfurter.dev`) and parses responses through a flexible JSON mapping layer so provider schema changes (e.g. `rates` vs `conversion_rates`) cannot break audit reconstruction.
- Cosmos DB audit store: every successful conversion persisted with the server-generated sub-second `DateTimeOffset` execution timestamp, the provider-returned date/sequence marker, input amount, currencies, rate, provider, stale-flag, and a stable audit id; a lookup endpoint lets an auditor retrieve any past conversion on demand.
- Startup provisioning in `src/backend/Program.cs`: best-effort ARM control-plane provisioning, then token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` / `CreateContainerIfNotExistsAsync`; startup proceeds only if database/container are available and fails hard if the data-plane create-if-not-exists fails.
- Configuration binding for all values exclusively from environment variables using the exact keys in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md`, with `DefaultAzureCredential` configured for the specific `ManagedIdentityClientId`.
- Frontend conversion form and audit-history view in `src/frontend`, with the API base URL injected at container runtime through the `__VITE_API_URL__` placeholder-replacement entrypoint script (never baked in at build time).
- Graceful failure handling: 503 `ProblemDetails` when the provider is unreachable and no fallback rate exists, 400 for invalid input, 404 for unknown audit id, and any stale/fallback rate explicitly flagged in both the API response and the audit document.

**Out of Scope:**
- New infrastructure provisioning — each participant already has a provisioned Cosmos DB instance and Azure Container App; the only resource creation this Spec covers is the database/container create-if-not-exists described in Known Constraints.
- Deployment mechanics — the Outer Loop's CD pipeline owns Azure Container App deployment, sidecar wiring, and CI; this Spec only constrains the code so that deployment succeeds.
- User authentication/authorization for enterprise analysts (presumed handled by existing platform auth).
- Bulk/scheduled reconciliation jobs, batch export to email or spreadsheets, manual approval workflows, invoicing, or billing.
- Aggressive caching/CDN caching of rates, circuit-breaker frameworks, or retry/backoff libraries beyond what is minimally required for the graceful-failure behavior described here.
- Re-architecting the strict `src/frontend` / `src/backend` folder layout or changing the deployed single-ACA sidecar topology.

**Feature Constraints:**
- Use a typed `IHttpClientFactory` client for the external provider call, registered in `src/backend/Program.cs`; never `new HttpClient()`.
- Parse provider JSON with `System.Text.Json` (`JsonDocument`/`JsonElement`) into a neutral internal model using property-name fallback (look up `conversion_rates` first, then `rates`); never deserialize directly into a hardcoded third-party schema class.
- Audit timestamp: capture `DateTimeOffset.UtcNow` at the moment the conversion executes and persist it with sub-second precision (at least 7 fractional-second digits); store the provider's own date/sequence marker in a separate field and never derive audit time from it.
- Cosmos document shape: partition key = tenant/analyst id (string); each audit item carries `id` (GUID), `tenantId`, `amount`, `fromCurrency`, `toCurrency`, `rate`, `provider`, `providerDate`, `serverTimestamp`, `rateIsStale`. Retrieval by audit id is a point read on (partition key, id).
- Error contract: invalid/missing currency codes or non-positive amount → 400 `ProblemDetails`; provider failure with no fallback → 503 `ProblemDetails` titled `RateProviderUnavailable`; unknown audit id → 404. Raw network/serialization exceptions must never reach the client.
- No cross-request rate caching: each conversion fetches a fresh provider rate unless the provider is unavailable, in which case the last successfully fetched rate for the currency pair may be reused — and it must be flagged `rateIsStale: true` in both the API response and the audit document so an auditor can always distinguish a live rate from a fallback (this is the explicit reconciliation of the "trustworthy amount" business need with the graceful-fallback Known Constraint).
- Frontend entrypoint: a generic shell script set as the container command that substitutes `__VITE_API_URL__` in the built `index.html` (or equivalent) with the runtime `VITE_API_URL` before the static server starts; the frontend code must never reference a hardcoded API origin.

**Expected Outcome:**
- `POST /api/currency/convert` with `{ "amount": 1000.00, "from": "USD", "to": "EUR" }` returns `200 OK` with a body containing `convertedAmount`, `rate`, `provider`, `providerDate`, `serverTimestamp` (UTC ISO-8601, sub-second precision), `rateIsStale: false`, and `auditId`; the same record is retrievable via `GET /api/currency/audit/{auditId}`.
  - Sample: provider returns rate `0.9183` → body contains `"convertedAmount": 918.30`, `"rate": 0.9183`, `"serverTimestamp": "2026-08-01T09:15:32.1234567Z"`, `"providerDate": "2026-08-01"`, `"auditId": "<guid>"`.
- When the provider returns 5xx / is unreachable and no fallback rate exists: response is `503` with a `ProblemDetails` body (`title: "RateProviderUnavailable"`) and no audit document is written.
- When the provider is unavailable but a prior successful rate exists for the pair: response is `200` with `"rateIsStale": true`, and the persisted audit document also stores `rateIsStale: true`.
- Invalid input (`"from": "ZZZ"`, or `amount <= 0`) → `400` `ProblemDetails`; `GET /api/currency/audit/{nonexistentId}` → `404`.
- Startup behavior: the app in `src/backend` starts only after token-authenticated data-plane create-if-not-exists succeeds; if it fails, the process exits non-zero.
- Repository checks pass: `src/backend/OuterloopLabApi.sln` exists and `dotnet build` / `dotnet test` invoked via the `.sln` succeed targeting `net10.0`; a repo-wide grep finds no connection strings, master keys, or account keys in code, configuration, or logs; every environment variable name used matches `docs\CONTAINER_ENVIRONMENT_VARIABLES.md`.

**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assumption: the feature should be implemented by modifying or creating code in `src/backend/Program.cs`, `src/backend/Controllers/CurrencyConversionsController.cs`, `src/backend/Models/CurrencyConversionRequest.cs`, `src/backend/Models/CurrencyConversionResponse.cs`, `src/backend/Models/CurrencyConversionAuditRecord.cs`, `src/backend/Services/CurrencyRateClient.cs`, `src/backend/Services/CurrencyConversionService.cs`, `src/backend/Repositories/AuditTrailRepository.cs`, `src/frontend/index.html`, `src/frontend/entrypoint.sh` (or the repo's equivalent runtime placeholder replacement script in that same folder), `src/frontend/src/main.tsx`, `src/frontend/src/App.tsx`, and `src/frontend/src/api.ts`; if any assumed file does not yet exist, create it at that exact path rather than moving the implementation outside `src/backend` or `src/frontend`.

**In Scope:**
- Add a backend HTTP endpoint at `POST /api/conversions` that accepts an amount, source currency, and target currency; fetches the current rate from the configured external provider; computes the converted amount; persists an immutable audit record in Cosmos DB; and returns both the conversion result and the audit identifier.
- Add a backend HTTP endpoint at `GET /api/conversions/{auditId}` that returns the persisted audit record for a previously executed conversion, including the original request values, applied rate, converted amount, backend execution timestamp, and provider date/sequence markers.
- Persist one Cosmos DB audit document per successful conversion containing at minimum: audit id, amount, source currency, target currency, exchange rate, converted amount, backend execution timestamp in UTC, provider base URL, provider date marker if present, and any provider sequence/reference marker if present.
- Implement a backend abstraction that maps the external provider response into an internal normalized rate model so the rest of the application does not depend on provider-specific JSON field names.
- Update `src/frontend` so the user can enter amount/from/to values, submit a conversion request to the runtime-configured API URL, immediately see the converted amount plus audit id, and retrieve a past conversion by entering an audit id.
- Preserve and use the runtime placeholder replacement flow in `src/frontend/index.html` so the frontend never bakes a fixed API URL into the built artifact.

**Out of Scope:**
- User authentication, user-specific authorization, or separate auditor-only user interfaces.
- Batch conversion uploads, scheduled conversions, or processing more than one conversion request in a single API call.
- Historical rate lookup for arbitrary backdated dates beyond the provider data returned for the live conversion request.
- Exporting audit records to CSV, PDF, email, or external compliance systems.
- Editing or deleting previously stored audit records.
- Supporting multiple external rate providers, provider failover orchestration, or rate caching beyond what is strictly needed for a single live lookup flow.

**Feature Constraints:**
- Use `IHttpClientFactory` for outbound currency-rate HTTP calls, with an explicit client registration in `src/backend/Program.cs` and a request timeout that fails fast enough to return a controlled API response.
- Treat all monetary values as `decimal` in backend models, calculations, and persistence; do not use `double` or `float` for exchange-rate arithmetic.
- Normalize the provider response into an internal DTO with stable fields such as `Rate`, `ProviderDateMarker`, `ProviderReferenceMarker`, `BaseCurrency`, and `TargetCurrency` before any business logic or persistence runs.
- Generate the audit identifier on the backend as a new opaque id (for example a GUID string) and persist the record as immutable once created.
- For invalid client input (missing currency codes, identical source/target currency if the implementation chooses to reject it, or amount less than or equal to zero), return `ProblemDetails` with HTTP 400 rather than ad hoc error shapes.
- For upstream timeout, unreachable provider, or unparseable provider payload, return `ProblemDetails` with HTTP 503 and a stable domain message instead of leaking raw exception text.
- Surface the returned audit id prominently in `src/frontend/src/App.tsx` and make the audit lookup action reusable without requiring the user to re-run the conversion.

**Expected Outcome:** A user can load the React app with `VITE_API_URL` resolved at container runtime, enter a request such as `{ "amount": 100.00, "fromCurrency": "USD", "toCurrency": "EUR" }`, submit it once, and receive a successful response containing a newly generated audit id plus a conversion result that includes the original amount `100.00`, an exchange rate such as `0.92`, a converted amount `92.00`, a backend-generated UTC timestamp such as `2026-07-31T14:03:22.417Z`, and the provider date marker such as `2026-07-31`. The same audit id can then be supplied to `GET /api/conversions/{auditId}` and must return the persisted record with matching values so an auditor can reconstruct the transaction without relying on transient frontend state. If the external provider cannot be reached or returns an unusable payload, the conversion endpoint must return a `ProblemDetails` response with status `503` and no raw network or serialization stack trace in the response body.

**Expected Agent Output:** OpenCode should produce one implementation change set that: (1) adds or updates the backend files needed for request handling, provider normalization, Cosmos persistence, and startup/service registration under `src/backend`; (2) adds or updates the frontend files needed for runtime API configuration, conversion submission, result display, and audit lookup under `src/frontend`; and (3) includes automated verification for at least these three cases: successful conversion persistence, successful retrieval of a stored audit record by audit id, and a controlled `503 ProblemDetails` response when the upstream rate provider fails.

**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assuming a standard Vite React layout under `src/frontend`, the frontend entrypoints are expected to be `src/frontend/index.html`, `src/frontend/src/main.tsx`, and `src/frontend/src/App.tsx`, with any feature-specific UI or API helper files added under `src/frontend/src`. On the backend, the implementation must center on `src/backend/Program.cs` and the required solution file `src/backend/OuterloopLabApi.sln`, with additional endpoint, provider-adapter, domain-model, and Cosmos persistence files added under `src/backend`. The feature should be implemented as an in-app conversion workflow where the frontend calls the backend, the backend calls the external rate provider, records an audit document in Cosmos DB, and exposes a history query for audit retrieval.

**In Scope:**
- Add a backend HTTP endpoint that accepts a conversion request with source currency, target currency, and amount, obtains the live rate from the configured external provider, computes the converted amount, and returns both the result and the persisted audit metadata.
- Add backend persistence for an audit trail record containing the original request values, normalized provider rate data, the backend-generated execution timestamp, and the persisted record identifier needed for later retrieval.
- Add a backend HTTP endpoint that returns prior conversion records in reverse chronological order so an analyst can retrieve past conversions for audit review.
- Add a frontend form under `src/frontend` that lets the user enter amount, source currency, and target currency, submits the request to the backend, and displays the converted amount, rate, provider date marker, and exact execution timestamp returned by the backend.
- Add a frontend audit-history view under `src/frontend` that fetches and displays previously recorded conversions with enough detail to reconstruct what happened during a past transaction.
- Wire runtime API base URL handling so the frontend uses the runtime-injected `VITE_API_URL` value rather than a build-time constant when calling the backend.

**Out of Scope:**
- Bulk import of settlements, CSV upload, or batch conversion workflows.
- User authentication, role management, or per-user authorization rules.
- Editing or deleting historical audit records after they are created.
- Background polling, scheduled rate refresh jobs, or long-term rate caching strategies.
- Multi-provider failover orchestration beyond the single configured base URL and graceful error handling required by Known Constraints.

**Feature Constraints:**
- The backend should isolate external exchange-rate parsing behind a dedicated abstraction such as a provider service plus a normalized internal result model, so controller or endpoint code never depends directly on provider-specific property names.
- External rate retrieval should use `IHttpClientFactory` with a named or typed client configured from `CURRENCY_API_BASE_URL`.
- Audit records should be stored in a single Cosmos container with a stable document shape that includes at minimum: `id`, `sourceCurrency`, `targetCurrency`, `originalAmount`, `conversionRate`, `convertedAmount`, `providerDateMarker`, `providerSequenceMarker` when available, and `executedAtUtc` as a backend-generated UTC timestamp.
- Monetary values should be handled with `decimal` on the backend, and the API response should return amounts rounded to two fractional digits for display while preserving the underlying rate used for the calculation in the audit record.
- Backend failures from the external provider should be translated into domain-safe HTTP responses using `ProblemDetails`; raw exception text, stack traces, and raw third-party payloads must not be returned to the frontend.
- The frontend must call only the application backend for conversions and history; it must never call the external currency API directly from the browser.

**Expected Outcome:** A user can open the app, enter a request such as `100.00 USD` to `EUR`, and receive a backend-sourced result based on the live provider response. For example, if the provider returns data equivalent to a rate of `0.92` with a provider date marker of `2026-08-01`, the API should return a converted amount of `92.00`, and the persisted audit record should include the original amount `100.00`, source currency `USD`, target currency `EUR`, conversion rate `0.92`, converted amount `92.00`, provider date marker `2026-08-01`, and a backend-generated `executedAtUtc` timestamp such as `2026-08-01T14:03:22.481Z`. A subsequent history request should include that same record so an auditor can reconstruct the transaction. If the provider call fails, the backend should return a `ProblemDetails` response with a clear domain message and an appropriate 5xx status instead of a raw network or JSON parsing exception.

**Expected Agent Output:** OpenCode should produce a concrete implementation under `src/backend` and `src/frontend` that adds one conversion submission flow and one audit-history retrieval flow, keeps `src/backend/OuterloopLabApi.sln` as the backend build entrypoint, updates runtime frontend API URL usage, and introduces any required backend models, services, and endpoint wiring needed to persist and read audit records through Cosmos DB. The resulting change set should leave the application buildable on the required stack versions and should not modify files outside the allowed solution structure unless strictly necessary to satisfy the Known Constraints.

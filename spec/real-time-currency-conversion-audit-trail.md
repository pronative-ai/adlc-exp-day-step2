**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assumption where filenames are ambiguous: the implementation should update `src/backend/Program.cs` for startup wiring, token-authenticated Cosmos provisioning, and outbound currency-provider client registration; `src/backend/OuterloopLabApi.sln` for the required solution-based build/test entrypoint; the existing backend web API project file already referenced by that solution under `src/backend`; `src/frontend/index.html` for the `__VITE_API_URL__` runtime placeholder; and the existing Vite application bootstrap and screen files at `src/frontend/src/main.tsx` and `src/frontend/src/App.tsx` (or the same exact paths with `.jsx`/`.js` if that is how the project is currently scaffolded) to add the conversion form, result rendering, and audit lookup UI.

**In Scope:**
- Add a backend endpoint in `src/backend` that accepts a conversion request with source currency, target currency, and amount, calls the external provider using `CURRENCY_API_BASE_URL`, normalizes the provider response, and returns the converted amount plus audit metadata.
- Persist one immutable audit-trail document per successful conversion in Cosmos DB, including the original request values, normalized rate, converted amount, backend-generated execution timestamp, and any provider-supplied date or sequence markers.
- Add a backend endpoint in `src/backend` that retrieves prior conversion audit records by identifier and/or a recent list view suitable for an auditor-facing lookup workflow.
- Add frontend UI in `src/frontend` for entering amount/source currency/target currency, displaying the conversion result immediately after the API responds, and retrieving previously recorded conversions for audit review.
- Surface graceful error states in both API and UI when the external rate provider cannot be reached or returns unusable data, without persisting a partial audit record.

**Out of Scope:**
- Historical rate backfilling for dates other than the provider data returned for the live request.
- Bulk conversion uploads, CSV export, or spreadsheet-style batch workflows.
- User authentication, authorization, tenant isolation redesign, or any role-management changes beyond the current app behavior.
- Editing or deleting audit-trail records after creation.
- Background polling, scheduled rate refresh jobs, or speculative caching layers.

**Feature Constraints:**
- Use `IHttpClientFactory` for the external currency-rate call so timeout, retry, and error translation behavior is isolated from the controller/endpoint code.
- Introduce a provider-mapping abstraction that converts third-party JSON into an internal normalized result contract; the rest of the application must read only the normalized contract, not raw provider fields.
- Store monetary inputs, rate, and converted output as `decimal` values and serialize them culture-invariantly so audit replays are numerically stable.
- Persist audit documents as append-only records with a generated immutable identifier; a failed provider call must return a domain-level error response and must not create an audit document.
- Return API failures as `ProblemDetails`; for an upstream provider failure or unusable provider payload, return HTTP 503 with a stable application error title/detail instead of a raw exception message.
- Generate the authoritative execution timestamp on the backend in UTC with full available precision; the frontend may display it but must not originate or overwrite it.
- Keep the frontend API base URL consumption limited to the runtime-injected `VITE_API_URL` placeholder flow in `src/frontend/index.html`; do not bake environment-specific API URLs into the built assets.

**Expected Outcome:** A treasury analyst can submit a request such as `{ amount: 100.00, fromCurrency: "USD", toCurrency: "EUR" }` from the UI, receive a successful response showing a trustworthy converted amount such as `{ rate: 0.92, convertedAmount: 92.00 }`, and know that the backend also stored an audit record containing at least: a unique audit id, `amount = 100.00`, `fromCurrency = "USD"`, `toCurrency = "EUR"`, `rate = 0.92`, `convertedAmount = 92.00`, a backend-generated UTC execution timestamp such as `2026-08-01T14:03:12.456Z`, and the provider's own marker such as `providerDate = "2026-08-01"` (plus any provider sequence marker if available). When an auditor later requests that conversion, the lookup endpoint/UI returns the same stored values without recomputation. If the upstream provider is unavailable or returns an unmappable payload, the API responds with `ProblemDetails` and HTTP 503, the UI shows a clear failure state, and no audit document is written for that failed attempt. Completion is checkable by a successful frontend production build, a successful backend build/test invocation against `src/backend/OuterloopLabApi.sln`, and manual/API verification of one successful conversion plus one failed-provider scenario.

It should also update or create tests that verify the success path and the upstream-failure path, and it should finish by reporting the exact verification commands/results for the frontend build and the backend solution-based build/test run using `src/backend/OuterloopLabApi.sln`.

**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** The implementation should touch `src/backend/OuterloopLabApi.sln`, `src/backend/Program.cs`, `src/backend/Configuration/CurrencyApiOptions.cs`, `src/backend/Configuration/CosmosOptions.cs`, `src/backend/Models/CurrencyConversionAuditRecord.cs`, `src/backend/Services/ExternalRateProviderClient.cs`, `src/backend/Services/CurrencyConversionService.cs`, `src/backend/Services/CurrencyConversionAuditRepository.cs`, `src/backend/Endpoints/CurrencyConversionEndpoints.cs`, `src/frontend/index.html`, `src/frontend/package.json`, `src/frontend/src/App.tsx`, `src/frontend/src/components/CurrencyConversionForm.tsx`, and `src/frontend/src/components/ConversionAuditLookup.tsx`. Assumption: audit retrieval is by a generated conversion/audit ID returned after each successful conversion because no broader search workflow was requested in the business intent.

**In Scope:**
- Add a backend `POST /api/conversions` flow that validates amount and ISO currency codes, fetches a live rate from the configured provider base URL, normalizes the provider response into an internal quote model, computes the converted amount, and returns the audit ID, rate, provider markers, and backend execution timestamp.
- Persist one immutable Cosmos DB audit document per successful conversion containing the source currency, target currency, original amount, converted amount, exact rate used, backend execution timestamp, provider date/sequence markers, and the provider base URL used for the lookup.
- Add a backend `GET /api/conversions/{auditId}` flow that returns the stored audit record exactly as saved, without recalculating against a newer rate.
- Add startup provisioning in `src/backend/Program.cs` that performs best-effort ARM database/container creation, then mandatory token-authenticated Cosmos SDK `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` checks before the app starts serving requests.
- Add a frontend conversion screen that displays the live converted amount, rate, execution timestamp, and returned audit ID immediately after submission.
- Add a frontend audit lookup screen that fetches and displays a saved conversion by audit ID.
- Add focused automated coverage for provider-response normalization, conversion persistence/retrieval, and error mapping for upstream failure paths.

**Out of Scope:**
- Batch import/export of conversions.
- Arbitrary historical-date or forward-dated rate selection beyond the provider's latest available quote.
- User/role management, SSO, or auditor-specific authorization changes.
- Background polling, scheduled rate preloading, or alerting on exchange-rate movements.
- Reporting dashboards, PDF exports, or CSV audit extracts.

**Feature Constraints:**
- Use `IHttpClientFactory` with a typed client for outbound rate-provider calls, and isolate provider-specific parsing behind an interface that returns a normalized internal quote object.
- Parse upstream JSON with `System.Text.Json` using tolerant property access (`JsonDocument`, `JsonElement`, or equivalent flexible mapping) so the implementation can read provider markers such as `rates`, `conversion_rates`, `date`, or similarly named fields without binding the app to one fixed schema.
- Use `decimal` for monetary calculations, normalize submitted currency codes to uppercase before processing, round the returned converted amount to 2 decimal places for API/UI display, and persist the exact rate value used for reconstruction.
- Represent domain and upstream failures with explicit domain exceptions mapped to RFC 7807 `ProblemDetails` responses: `400` for invalid input, `404` for missing audit records, and `503` for unavailable or unmappable provider responses.
- Generate the backend execution timestamp from a single injectable clock source at the moment the normalized quote is accepted, and persist that exact value with the audit record so later reads do not regenerate timestamps.
- Provision the Cosmos container with partition key `/id` so audit retrieval by audit ID can be implemented as a deterministic point read.
- Persist the audit document immutably after a successful conversion; lookup endpoints must return stored values only and must not re-hit the external provider.

**Expected Outcome:** A treasury analyst can open the UI, enter `100.00` as amount, `USD` as source currency, and `EUR` as target currency, submit once, and receive a successful result such as `{ auditId: "8f8af6e4-4d0a-4c3d-95a0-7d8eb7c8d4f9", sourceCurrency: "USD", targetCurrency: "EUR", originalAmount: 100.00, rate: 0.92, convertedAmount: 92.00, providerDate: "2026-08-01", providerSequenceMarker: null, executedAtUtc: "2026-08-01T14:32:18.451Z" }` when the normalized upstream quote is `0.92` for that pair. The same `auditId` must later return the same values through `GET /api/conversions/{auditId}` without recalculating against a newer rate. If the external provider cannot be reached or its payload cannot be normalized, the conversion endpoint must return a `ProblemDetails` response with HTTP `503` and no raw network or serialization exception text; if the audit ID does not exist, the lookup endpoint must return `404` `ProblemDetails`.

**Expected Agent Output:** A change set that updates `src/backend/OuterloopLabApi.sln`, backend startup/configuration/package references, and `src/frontend/index.html` plus `src/frontend/src` UI files; adds exactly one conversion-create API and exactly one audit-lookup API; adds the provider abstraction, Cosmos audit repository, immutable audit persistence model, and runtime API URL placeholder replacement support; and includes focused automated tests proving rate normalization, `503` upstream failure handling, and immutable audit lookup. Verification should include `dotnet test src/backend/OuterloopLabApi.sln` and the frontend build command from `src/frontend` using Node 24.*.
